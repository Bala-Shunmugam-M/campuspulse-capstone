# Campus Compliance Platform — Design

**Status:** draft for review
**Date:** 2026-09-16
**Author:** Bala Shunmugam (Ruthra)
**Relates to:** CampusPulse capstone — https://github.com/Bala-Shunmugam-M/campuspulse-capstone

---

## 1. Context

CampusPulse today is a data layer: a PostgreSQL schema on Supabase, a synthetic
data engine, a 47-check integrity audit and 14 analytics queries, all driven from
Python. It models **facility incidents** — a broken water dispenser, a failed AC
unit — and it proves the modelling is sound. What it has never had is a user.
Every row in it was generated by a script.

This project adds the missing half: a real web platform, in the adjacent domain of
**campus compliance and conduct** — policy violations, misconduct reports,
investigations, sanctions. It is a capstone deliverable and a data-generating
system, and those two goals pull in the same direction only if the data is
generated by genuine use of genuine code paths.

### Goals

1. A platform that behaves like an institutional system, not a demo: real
   authentication, real authorisation on every sensitive route, real workflows
   with states that cannot be skipped, and a real audit trail.
2. A dataset that is **both structured and unstructured**, produced as a
   by-product of use rather than inserted by a fixture script.
3. A codebase a marker can read: clear boundaries, no stubs, no dead scaffolding.

### Non-goals

- Replacing or modifying the existing `campuspulse` schema. It is published and
  its integrity audit passes; this design treats it as read-only.
- Email delivery, SMS, or SSO integration. Notifications are in-app and
  persisted; the delivery channel is modelled but not wired to a provider.
- Production-grade malware scanning. Evidence files carry a `scan_status` column
  and the pipeline hook, with a no-op scanner. Pretending otherwise would be
  dishonest.

## 2. Scope and phasing

One spec, three implementation phases. Each phase ends with a system that runs.

| Phase | Delivers |
|---|---|
| **1 — Spine** | Auth, RBAC, incident intake (including anonymous), case queue and detail, audit log, seed data |
| **2 — Workflow** | Assignment, guarded status transitions, investigation notes, outcomes and sanctions, evidence upload, notifications and activity feed |
| **3 — Knowledge & insight** | Versioned policy library with acknowledgements and search, officer/admin dashboards, campus directory, traffic simulator |

Two things sit in Phase 1 that are commonly deferred, deliberately:

- **Audit logging**, because a compliance record whose history begins in Phase 3
  has no history. Every mutation from the first commit writes an audit event in
  the same transaction.
- **Soft deletes**, because adding `deleted_at` later means backfilling every
  table and auditing every query that already assumed hard deletion.

## 3. Architecture

### 3.1 Repository layout

The platform lives inside the existing capstone repository, beside the Python
project rather than replacing it:

```
CampusPulse/
├── 0*_*.py, db_config.py, sql/        # existing Python data project — untouched
├── docs/                              # existing docs + this spec
└── webapp/                            # this project
    ├── docker-compose.yml             # Postgres + MinIO for local development
    ├── prisma/
    │   ├── schema.prisma
    │   ├── migrations/
    │   ├── fixtures/campuspulse_min.sql
    │   └── seed.ts
    ├── src/
    │   ├── app/                       # App Router: routes and layouts
    │   ├── components/                # presentational components
    │   ├── lib/
    │   │   ├── auth/                  # Auth.js config, RBAC helpers
    │   │   ├── audit/                 # withAudit()
    │   │   ├── cases/                 # state machine, SLA
    │   │   ├── storage/               # StorageDriver implementations
    │   │   └── validation/            # Zod schemas, shared client and server
    │   └── server/                    # service layer, the only code touching Prisma
    └── scripts/
        ├── simulate.ts                # traffic simulator (drives real HTTP)
        └── verify.ts                  # invariant checks over whatever is in the DB
```

The rule that keeps this navigable: **route handlers and server actions never
touch Prisma directly.** They validate input, call a service in `src/server/`,
and render. Services own transactions and audit writes. This is what makes the
audit guarantee checkable — there is exactly one layer to inspect.

### 3.2 Stack

Next.js 15 (App Router), React 19, TypeScript (strict), Tailwind, Prisma,
Auth.js v5, Zod, Argon2id. Server Components for reads and Server Actions for
mutations; TanStack Query only where the UI is genuinely interactive, which in
practice is the case queue's filter-and-paginate view.

### 3.3 Two database targets, one schema

Prisma manages the `compliance` schema only. `campuspulse` is external and
read-only, referenced through foreign keys using Prisma's `multiSchema`.

- **Development:** Postgres in Docker. Instant, offline, safe to reset. Because
  a local database has no `campuspulse` schema, `prisma/fixtures/campuspulse_min.sql`
  creates the four referenced tables (`institutions`, `users`, `locations`,
  `categories`) with the same shape, and the seed populates them.
- **Shared:** the existing Supabase project, where `campuspulse` already holds
  42,763 real rows and compliance cases can be joined against facility incidents.

This split exists because the Supabase project is on a free tier that sleeps
after about a week idle. Developing directly against it means every migration is
a network round-trip to a database that may be asleep, and a bad migration lands
on the real data. Developing locally and promoting migrations is what a team
would do, and it is the honest answer to "how do you test a schema change".

## 4. Data model

All tables below are in the `compliance` schema. Every table carries
`created_at timestamptz NOT NULL DEFAULT now()` and, except where noted,
`updated_at` and `deleted_at timestamptz` for soft deletion.

Multi-tenancy follows the pattern the existing schema already established:
`institution_id` is carried on every root record, and composite foreign keys
against `campuspulse.users(id, institution_id)` make it structurally impossible
for a record to reference a user from another tenant.

Two extensions are required and created by the first migration: `citext`, for
case-insensitive email comparison without scattering `lower()` through every
query, and `pgcrypto`, for `gen_random_uuid()` — the same function the existing
`campuspulse` schema already relies on.

### 4.1 Enums

```sql
compliance_role     ('reporter','officer','investigator','admin','dpo')
severity            ('low','moderate','high','severe')
report_channel      ('web','kiosk','email_ingest','phone_transcribed')
report_status       ('received','triaged','merged','rejected')
case_status         ('submitted','triaged','under_investigation',
                     'pending_decision','resolved','closed','dismissed','appealed')
party_role          ('complainant','respondent','witness','advisor')
note_visibility     ('internal','shared_with_parties','reporter_visible')
finding             ('upheld','partially_upheld','not_upheld','inconclusive')
sanction_type       ('warning','written_reprimand','probation','suspension',
                     'community_service','restitution','referral','no_action')
confidentiality     ('standard','restricted','sealed')
scan_status         ('pending','clean','flagged','skipped')
```

### 4.2 Identity

**`user_accounts`** — authentication credentials for an existing campus person.
The platform does not invent people; it gives accounts to rows that already exist
in `campuspulse.users`.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid NOT NULL UNIQUE | → `campuspulse.users(id)` |
| `institution_id` | uuid NOT NULL | denormalised for the composite FK |
| `email` | citext NOT NULL | login handle, mirrors the campus record |
| `password_hash` | text NOT NULL | Argon2id |
| `password_changed_at` | timestamptz | |
| `failed_login_count` | int NOT NULL DEFAULT 0 | |
| `locked_until` | timestamptz | set by lockout policy |
| `last_login_at` | timestamptz | |
| `must_change_password` | boolean NOT NULL DEFAULT false | true for seeded accounts |

Constraints: `FOREIGN KEY (user_id, institution_id) REFERENCES campuspulse.users(id, institution_id)`,
`UNIQUE (institution_id, email)`.

**`role_assignments`** — roles are granted, not attributes.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `user_account_id` | uuid NOT NULL | → `user_accounts`, ON DELETE CASCADE |
| `role` | compliance_role NOT NULL | |
| `scope_department` | text NULL | NULL means institution-wide |
| `granted_by` | uuid NULL | → `user_accounts` |
| `granted_at` | timestamptz NOT NULL | |
| `revoked_at` | timestamptz NULL | revocation is soft, for audit |

`UNIQUE (user_account_id, role, scope_department) WHERE revoked_at IS NULL`.

A partial unique index rather than a plain one, because the same role may be
granted, revoked and granted again — and the history has to survive.

### 4.3 Intake

**`reports`** — what a person submits. One report is one person's account of one
thing; several reports may describe the same underlying case, exactly as the
existing project separates `reports` from `incidents`.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `institution_id` | uuid NOT NULL | → `campuspulse.institutions(id)` |
| `reference_code` | text NOT NULL UNIQUE | e.g. `CR-7QK2-M4X9` |
| `access_secret_hash` | text NULL | anonymous reports only |
| `reporter_user_id` | uuid NULL | → `user_accounts`; NULL means anonymous |
| `is_anonymous` | boolean NOT NULL | |
| `category_id` | uuid NULL | → `campuspulse.categories(id)` |
| `location_id` | uuid NULL | → `campuspulse.locations(id)` |
| `occurred_at` | timestamptz NULL | when it happened |
| `submitted_at` | timestamptz NOT NULL | when it was reported |
| `title` | text NOT NULL | |
| `description` | text NOT NULL | **unstructured** |
| `search_tsv` | tsvector GENERATED STORED | over title and description |
| `severity_self_reported` | severity NOT NULL | what the reporter thinks |
| `channel` | report_channel NOT NULL | |
| `status` | report_status NOT NULL DEFAULT 'received' | |
| `case_id` | uuid NULL | → `cases`; set at triage |
| `ip_hash`, `user_agent` | text | for abuse investigation, hashed |

The anonymity invariant is enforced in the database, not only in code:

```sql
CHECK (
  (is_anonymous     AND reporter_user_id IS NULL     AND access_secret_hash IS NOT NULL)
  OR
  (NOT is_anonymous AND reporter_user_id IS NOT NULL AND access_secret_hash IS NULL)
)
```

This matters because the failure mode — an "anonymous" report that silently
carries a reporter id — is invisible in the UI and catastrophic in a compliance
system. A CHECK constraint makes it unrepresentable.

`report_statements` holds follow-up accounts added later by the same reporter
(`report_id`, `body text`, `submitted_at`), so a report can grow without its
original text being edited.

### 4.4 Cases

**`cases`** — the unit of work. Created at triage, possibly from several reports.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `institution_id` | uuid NOT NULL | |
| `case_number` | text NOT NULL | `CASE-2026-0001`, unique per institution and year |
| `title` | text NOT NULL | |
| `summary` | text NULL | **unstructured**, written by the officer |
| `category_id` | uuid NULL | → `campuspulse.categories(id)` |
| `severity` | severity NOT NULL | officer's assessment, may differ from reporter's |
| `status` | case_status NOT NULL DEFAULT 'submitted' | |
| `assigned_officer_id` | uuid NULL | → `user_accounts` |
| `opened_at` | timestamptz NOT NULL | |
| `sla_due_at` | timestamptz NOT NULL | derived from severity at creation |
| `first_response_at` | timestamptz NULL | first officer action |
| `resolved_at`, `closed_at` | timestamptz NULL | |
| `confidentiality` | confidentiality NOT NULL DEFAULT 'standard' | gates visibility |

`UNIQUE (institution_id, case_number)`.

Supporting tables:

- **`case_reports`** — junction, many reports to one case, mirroring
  `campuspulse.incident_reports`. Carries `is_primary boolean`.
- **`case_parties`** — `case_id`, `user_account_id NULL`, `external_name text NULL`,
  `party_role`, `is_anonymous boolean`. A party may be someone with no account.
- **`case_notes`** — `case_id`, `author_id`, `body text` (**unstructured**),
  `visibility note_visibility`. Soft-deletable, never hard-deleted.
- **`case_status_history`** — `case_id`, `from_status`, `to_status`, `changed_by`,
  `reason text`, `changed_at`. Append-only.
- **`outcomes`** — one per case: `finding`, `rationale text` (**unstructured**),
  `decided_by`, `decided_at`. `UNIQUE (case_id)`.
- **`sanctions`** — `outcome_id`, `subject_party_id`, `sanction_type`,
  `description text`, `effective_from`, `effective_to`, `status`.

### 4.5 Policy library

- **`policies`** — `institution_id`, `code`, `title`, `owner_department`, `is_active`.
- **`policy_versions`** — `policy_id`, `version_no int`, `body_markdown text`
  (**unstructured**), `summary text`, `effective_from date`, `effective_to date`,
  `published_by`, `published_at`, `body_tsv tsvector GENERATED STORED`.
  `UNIQUE (policy_id, version_no)`.
- **`policy_acknowledgements`** — `policy_version_id`, `user_account_id`,
  `acknowledged_at`. `UNIQUE (policy_version_id, user_account_id)`.

Published versions are immutable. A `BEFORE UPDATE` trigger raises an exception
on any column other than `effective_to`, because "the policy said something
different when I signed it" is precisely the claim the table exists to refute.
Superseding a policy means inserting version *n+1*.

### 4.6 Evidence

**`evidence_files`** holds metadata only; bytes live in object storage.

`id`, `institution_id`, `case_id NULL`, `report_id NULL`, `uploaded_by NULL`
(anonymous uploads are permitted), `storage_key text`, `original_filename text`,
`mime_type text` (**sniffed from content, never trusted from the client**),
`byte_size bigint`, `sha256 char(64)`, `scan_status`, `created_at`, `deleted_at`.

`CHECK (case_id IS NOT NULL OR report_id IS NOT NULL)` — an orphan evidence file
is a bug, so the schema refuses to hold one.

### 4.7 Audit and notification

**`audit_events`** — append-only, high volume, so `bigserial` rather than uuid.

`id`, `institution_id`, `actor_user_account_id NULL`, `actor_label text`
(`'anonymous'`, `'system:simulator'`), `action text` (`'case.status_changed'`),
`entity_type text`, `entity_id uuid`, `before jsonb`, `after jsonb`,
`request_id uuid`, `ip_hash`, `user_agent`, `occurred_at`.

No `updated_at`, no `deleted_at`: the table is append-only, enforced by revoking
UPDATE and DELETE from the application role and by a trigger that raises on both.
An audit log the application can edit is not an audit log.

**`notifications`** — `recipient_id`, `case_id NULL`, `channel`
(reusing the existing channel vocabulary), `subject`, `body text`, `is_read`,
`read_at`, `created_at`.

**`activity_feed`** is a view over `audit_events` filtered to user-visible actions
and joined to actor names, not a separate table — the same event should not be
written twice and risk disagreeing with itself.

### 4.8 Indexing

Beyond primary and foreign keys: GIN on both `tsvector` columns; composite
`(institution_id, status, sla_due_at)` on `cases` for the officer queue;
`(assigned_officer_id, status)` for workload views;
`(entity_type, entity_id, occurred_at DESC)` on `audit_events` for record history;
partial `(recipient_id) WHERE is_read = false` for the notification badge.

## 5. Authentication, authorisation and anonymous reporting

### 5.1 Why credentials rather than a managed provider

Auth.js v5 with a Credentials provider, Argon2id hashing. The alternative — a
managed provider or magic links — needs an email service and an internet
round-trip to demonstrate. A marker must be able to clone the repository, run
`docker compose up`, and log in as each role within a minute. Seeded accounts
with known passwords make that possible; every seeded account carries
`must_change_password = true` so the pattern is not mistaken for a real
deployment posture.

Sessions are database-backed rather than JWT. A JWT cannot be revoked before it
expires, and "revoke this officer's access now" is a requirement a compliance
system genuinely has.

Password policy: minimum 12 characters, checked against a small list of common
passwords, Argon2id with per-password salt. Five failed attempts within fifteen
minutes sets `locked_until`. Both the success and the failure write audit events —
failed logins are exactly what an investigator needs and are usually missing.

### 5.2 Authorisation

Authorisation is a server-side function, never a UI concern. Hiding a button is
presentation; the check happens in the service layer:

```ts
// src/lib/auth/rbac.ts
export async function requireRole(
  session: Session | null,
  roles: ComplianceRole[],
  scope?: { institutionId: string; department?: string }
): Promise<AuthorisedActor>   // throws ForbiddenError otherwise
```

Every server action and route handler that mutates or reads non-public data calls
`requireRole` as its first statement. The rule is mechanical, so it is reviewable:
**if a function in `src/server/` does not begin with an authorisation call, it is
a bug.** A test walks the service directory and asserts this, so the invariant
cannot rot silently.

Role capabilities:

| Capability | reporter | officer | investigator | admin | dpo |
|---|:--:|:--:|:--:|:--:|:--:|
| Submit a report | ✓ | ✓ | ✓ | ✓ | ✓ |
| See own reports | ✓ | ✓ | ✓ | ✓ | ✓ |
| See the case queue | | ✓ | ✓ | ✓ | |
| Triage, assign | | ✓ | | ✓ | |
| Add investigation notes | | ✓ | ✓ | ✓ | |
| Record outcome and sanctions | | ✓ | | ✓ | |
| Manage policies | | | | ✓ | |
| Grant and revoke roles | | | | ✓ | |
| Read audit log | | | | ✓ | ✓ |
| Read `sealed` cases | | | | | ✓ |

`sealed` confidentiality exists so the design does not pretend an admin should
see everything. Cases involving an admin are sealed to the data protection
officer, and the admin's own attempt to open one is recorded.

### 5.3 Anonymous reporting

The hard part is letting someone follow up without identifying them.

**Submission.** No account, no session. The server generates two values:

- `reference_code` — short and human-readable (`CR-7QK2-M4X9`), safe to speak
  aloud or write down, stored in clear because it is an identifier, not a secret.
- `access_secret` — 32 bytes of CSPRNG output, base32-encoded, **displayed
  exactly once** and stored only as an Argon2id hash.

Both are shown on a confirmation screen that warns the secret cannot be
recovered. Status lookup requires both.

A reference code alone would be enough for enumeration: codes are short, the
space is guessable, and the contents are sensitive. Requiring a secret that the
server cannot reproduce means a leaked code discloses nothing. The trade-off is
real and stated plainly: **lose the secret and the report cannot be followed
up.** That is the correct failure direction for anonymity, and the UI says so.

**Rate limiting.** Lookup is limited per IP and per reference code, with failures
audited. Without this the secret is brute-forceable at leisure.

**What the reporter sees.** Status, non-privileged status history, and notes
explicitly marked `reporter_visible`. Never the investigator's internal notes,
never other parties' identities.

**What anonymity does not mean.** `ip_hash` and `user_agent` are retained, hashed
with a server-side pepper, so coordinated abuse can be investigated without
identifying an individual reporter. This is documented in the UI rather than
hidden, because a system that claims more anonymity than it provides is worse
than one that is clear about its limits.

## 6. Case workflow

```
submitted ──▶ triaged ──▶ under_investigation ──▶ pending_decision ──▶ resolved ──▶ closed
     │            │                                                                   │
     └──▶ dismissed ◀──────────────────────────────────────────────────────────────────┘
                                                      closed ──▶ appealed ──▶ under_investigation
```

Allowed transitions and the role each requires live in one map in
`src/lib/cases/transitions.ts`. A transition performs, in a single transaction:
the `cases.status` update, a `case_status_history` row, an `audit_events` row,
and any notifications. Either all of it happens or none of it does.

SLA is derived from severity at case creation (`severe` 24h, `high` 72h,
`moderate` 7d, `low` 14d) and stored on the row rather than computed at read
time, so changing the policy later does not silently rewrite history — the same
reasoning the existing Python project applies to `sla_due_at`.

## 7. Evidence and storage

A `StorageDriver` interface with two implementations: local disk for development,
Supabase Storage for the shared instance. Files are never served from a static
path. A route handler authorises the request, then streams the object.

On upload: sniff the MIME type from content rather than trusting the header,
reject executables and archives by extension *and* by sniffed type, cap size,
compute sha256, store under a random key rather than the user's filename. The
original filename is metadata, never a path.

## 8. Data generation

This is the part that makes the project a data-generating system rather than a
seeded demo, and it is worth being precise about.

### 8.1 Seed versus simulate

**`prisma/seed.ts`** establishes the world: institutions, people, departments,
locations, categories, policies, role assignments. It is idempotent and writes
directly to the database, because a world is a fixture, not an event.

**`scripts/simulate.ts`** produces activity, and it does **not** write to the
database. It authenticates over HTTP as seeded users and drives the same
endpoints a browser drives.

The distinction matters. A script that inserts a case row can produce a case with
no audit trail, no status history, an SLA that was never computed, and a status
no transition would have allowed — data that looks plausible and is structurally
impossible. Driving real endpoints means generated data is, by construction,
data the application could have produced. Every simulated action leaves exactly
the audit rows, notifications and history a real action leaves.

### 8.2 The behavioural model

The simulator runs a population of agents, each a seeded user with a role and a
schedule. Agent behaviour is weighted, not uniform:

- **Reporters** submit at rates varying by hour and weekday, reusing the arrival
  model the Python generator already validated — weekday activity exceeds
  weekend, and reports cluster around class-change times. Roughly a third submit
  anonymously. Some file a follow-up statement days later; some never return.
- **Officers** triage from the queue, preferring older and higher-severity cases,
  assign, write notes, and move cases through the state machine. They do not act
  instantly: response latency is drawn from a distribution, which is what makes
  the SLA analytics meaningful rather than uniformly green.
- **Investigators** add notes and upload evidence at intervals across a case's life.
- **A minority of cases go wrong on purpose** — dismissed at triage, appealed
  after closure, reassigned mid-investigation. A dataset in which every case
  flows cleanly to `closed` teaches nothing and would make the dashboards lie.

Free text comes from templated fragments composed with Faker, seeded for
reproducibility, so descriptions and notes vary in length and register rather
than repeating a handful of strings.

### 8.3 What it produces

| Structured | Unstructured |
|---|---|
| Cases with real status histories and SLA outcomes | Report descriptions and follow-up statements |
| Assignment and workload distribution across officers | Investigation notes at several visibility levels |
| Outcomes and sanctions | Outcome rationales |
| Notifications, read and unread | Uploaded evidence files with real bytes |
| A complete audit trail of every action | Policy bodies in Markdown |
| Policy acknowledgement coverage | |

The simulator takes `--seed` and `--anchor` arguments, exactly as
`02_Insert_Data.py` does, so a run is reproducible. It is also the integration
test: a run that completes without an HTTP error has exercised every workflow
end to end, and a run that leaves the database failing its integrity checks has
found a bug.

### 8.4 Verification

A `scripts/verify.ts` in the spirit of the existing `03_Verify_Data.py` asserts
invariants over whatever the database holds:

- every case has at least one report, and its current status appears in its
  status history;
- no anonymous report carries a reporter id;
- every state transition present in history is one the state machine permits;
- every mutation has a corresponding audit event;
- no timestamp lies in the future; resolved precedes closed;
- published policy versions are unmodified since publication.

That last set is where the previous phase of this capstone found its real bugs,
and the same discipline applies here.

## 9. Non-functional requirements

**Validation.** One Zod schema per input, imported by both the client form and
the server action. The server never trusts the client's validation; it re-parses.

**Errors.** Typed domain errors (`ForbiddenError`, `NotFoundError`,
`InvalidTransitionError`) mapped to responses in one place. Error boundaries and
loading states per route segment. Internal messages are never returned to the
client.

**Accessibility.** Semantic landmarks, labelled form controls, visible focus,
keyboard-operable interactive elements, AA contrast. This is an institutional
system with a legal obligation, not a nicety.

**Responsive.** Desktop and tablet are primary; the reporting flow in particular
must work on a phone, because that is where an incident is reported from.

**Configuration.** All secrets through environment variables, `.env.example`
committed, `.env` git-ignored — the existing repository's convention, already
verified clean.

**Deployment.** `docker compose up` gives Postgres, MinIO and the app. A
multi-stage `Dockerfile` for the app itself. `README.md` covers setup,
architecture and the data-generation story.

## 10. Risks

| Risk | Response |
|---|---|
| Supabase free tier sleeps after ~1 week idle | Local Docker is the development target; the shared instance is resumed when needed and the README documents it |
| Cross-schema FKs complicate local development | `campuspulse_min.sql` fixture creates the referenced tables locally with matching shape |
| Scope is large for a capstone | Phased so each phase is independently demonstrable |
| Simulator-generated data mistaken for real activity | Every simulated actor writes `actor_label = 'system:simulator'` in the audit trail, so generated activity is always distinguishable |

## 11. Open questions

1. Should the platform read existing `campuspulse` facility incidents into its
   dashboards, or stay strictly within compliance? Cross-schema reporting is
   the strongest argument for the "extension" framing, but it widens Phase 3.
2. How many institutions should the seed create? The existing project uses three,
   which exercises tenant isolation properly; matching it keeps the two halves
   consistent.
